# VMerger: метрики качества агентов и дашборд

Дата: 23 октября 2026. Статус: спецификация измерений и демонстрация графиков; реальных прогонов агентов пока нет. Связанные документы: [качество и эксплуатация](quality-and-operations.md), [агенты](agents-and-effects.md), [архитектура](architecture.md).

## 1. Единица оценки и правила подсчёта

Оцениваем три уровня: конкретный инструмент/предложение, законченный запуск агента и готовый фильм после всей цепочки. Улучшение отдельного агента должно проверяться также на готовом фильме.

Тестовый случай (case) содержит неизменяемые исходники, запрос, доступные ресурсы и разметку. Проект может содержать несколько связанных случаев и правок. Для сравнения версий фиксируем suite_version, разбиение train/dev/holdout, аппаратный профиль, набор ресурсов и модель/промпт/инструменты. Исходный corpus_id и все его правки принадлежат одному разбиению: похожие фрагменты одной поездки не попадают одновременно в dev и holdout.

Начальный контрольный набор: 30 независимых проектов, минимум три вида правок на проект. Для каждого случая — три запуска; повтор не считается новым независимым проектом. В оценке конкретной роли фиксируем входы от предыдущих этапов, затем выполняем отдельный сквозной прогон всей цепочки.

Каждое измерение содержит metric_id, metric_version, case_id, trial, числитель, знаменатель, единицу, источник оценки и ссылки на доказательства. Обязательны n_projects, n_cases, n_runs, n_eligible, n_observed, n_missing. Знаменатель задаётся до выполнения; нельзя исключить неудобный результат после просмотра.

Правила:

- Нет применимых объектов — not_applicable с причиной, а не 100%. Нет оценки/результата — missing или failed, а не 0 баллов без пояснения.
- Таймаут, ошибка инструмента, исчерпание бюджета и отсутствие фильма остаются в знаменателе end_to_end_success.
- Художественные метрики рассчитываются для фактически оцениваемых результатов с отдельной долей покрытия; отсутствие фильма нельзя скрыть хорошим средним по оставшимся.
- Человеческая оценка, автоматический валидатор и LLM-оценка хранятся отдельными сериями. LLM не заменяет эталон для жёстких требований.
- По умолчанию считаем среднее по повторам, затем по случаям проекта и среднее по независимым проектам. Это macro-агрегация: длинный фильм не получает больше веса только из-за числа кадров.
- Micro-отношение суммарных числителей и знаменателей дополнительно показывается для диагностики. На графике всегда подписано, какой вариант используется.
- Критические нарушения агрегируются также абсолютным числом: одно нарушение не должно раствориться в среднем.
- Время и расходы учитывают все попытки; стоимость неизвестного вызова не принимается равной нулю.

Все численные цели ниже — стартовые критерии продукта, подлежащие проверке на размеченном наборе. Метрики художественного качества дают основание для сравнения версий; они не являются объективной гарантией «красивого фильма».

## 2. Общие показатели

| ID и единица | Точная формула / проверка | Источник и стартовый критерий |
|---|---|---|
| end_to_end_success, % | 100 × запусков с проверенным фильмом, всеми жёсткими требованиями и завершением до deadline / всех принятых применимых запусков | jobs + renders + валидаторы; ≥ 99%, отдельно число неуспехов |
| first_plan_valid, % | 100 × запусков, где первое предложение плана прошло schema/semantic validation / запусков, которым требовался план; отсутствие предложения до deadline — неуспех | Первый submit_edit_plan / proposal, версия валидатора; ≥ 95% |
| hard_violation_count, шт. | Число финальных результатов с хотя бы одним нарушенным жёстким правилом; отдельно количество нарушенных правил по типу | Независимый валидатор и размеченные обязательные условия; ровно 0 |
| tool_success, % | 100 × успешных завершённых вызовов / всех завершённых или просроченных вызовов; отдельно invalid_arguments, provider_error, access_denied | agent_steps; ≥ 98%, с разбиением причин и роли |
| evaluation_coverage, % | 100 × пригодных измерений / заранее определённых применимых измерений | Реестр случаев и наблюдений; 100% для обязательных проверок допуска |

hard_violation_count считается по реально выданным финальным результатам. Попытки небезопасной/некорректной операции, остановленные валидатором, учитываются отдельно и влияют на first_plan_valid/tool_success. Если финального результата нет, end_to_end_success равен 0; отсутствие нарушающего результата не означает успешное выполнение.

К жёстким правилам относятся доступ к проекту, действующая версия/аренда, наличие обязательного момента, исключение запрещённого пользователем фрагмента, сохранение закреплённого монтажа, допустимость ресурсов и воспроизведение файла. Для каждого правила нужен oracle: код, разметка или фактический результат проверки файла.

Графики: доли по версии с числителем/знаменателем и 95% интервалом; нарушения — отдельные столбцы по типу и версии. Красный статус любого критического нарушения не компенсируется стоимостью или субъективной оценкой.

## 3. Режиссёр / сценарист

| ID и единица | Как проверяем | Начальная цель | График |
|---|---|---|---|
| salient_event_coverage, % | 100 × Σ(w_i × covered_i) / Σw_i по релевантным сценарию значимым событиям | ≥ 90% | Точки по версии с интервалами; детализация по событию |
| unrequested_repetition, % | 100 × длительность непрошенных повторных моментов / длительность видеоряда | ≤ 5% | Распределение по проектам и среднее по версиям |
| supported_claims, % | 100 × подтверждённых проверяемых утверждений в титрах/сценарии / всех проверяемых утверждений | 100% для явно фактических подписей; неподтверждённые факты разбираются отдельно | Доля и абсолютное число неподтверждённых фактов |
| story_approval, % | 100 × случаев с итоговой человеческой оценкой связности ≥ 4 из 5 / оценённых случаев | ≥ 80% и отсутствие подтверждённой регрессии | Распределение 1–5 и доля одобрения |

Разметчик заранее задаёт event_id, вес w_i (1 — обычное, 2 — важное, 3 — центральное), допустимые альтернативные исходные интервалы и минимальную долю их сохранения. covered_i = 1, если хотя бы одна допустимая альтернатива представлена в итоговом плане с заданным покрытием; по умолчанию 80% длины размеченного смыслового интервала. Наблюдения нескольких камер одного события считаются одним событием. Жёсткое «оставь целиком» проверяется отдельно и требует полного сохранения в пределах точности таймкодов.

Для нескольких фильмов разметка указывает назначение события конкретной истории; одно и то же событие не требуется во всех фильмах. Если выбор структуры свободный, дополнительно проверяется покрытие всей подборки.

Повторы считаются по размеченным canonical_moment_id и пересечению исходных интервалов, с переводом повторной части во время результата после изменения скорости. Разрешённые пользователем повторы исключаются до подсчёта. Переход между двумя соседними кадрами сам по себе не образует повтор. Поиск визуальных дублей моделью — вспомогательный сигнал; контрольный oracle размечается человеком.

Для supported_claims проверяем места, даты, имена и утверждения о событиях по доступным подтверждениям. При отсутствии проверяемых утверждений — not_applicable. Система не обязана добавлять подписи ради улучшения метрики.

## 4. Музыкальный агент

| ID и единица | Как проверяем | Начальная цель | График |
|---|---|---|---|
| music_fit_approval, % | 100 × случаев с человеческой оценкой уместности музыки ≥ 4 / оценённых применимых случаев | ≥ 80% | Доля по версии с интервалами и распределение оценок |
| speech_mix_pass, % | 100 × речевых окон, где уровень обработанной речи выше музыки минимум на δ dB / речевых окон с наложенной музыкой | ≥ 95%, стартовое δ = 6 dB | Распределение разницы уровней, линия δ и доля прошедших окон |
| speech_intelligibility_approval, % | 100 × случаев, где речь без дополнительного усилия понятна по человеческой проверке / случаев с речью поверх музыки | ≥ 95% | Доля и список проблемных таймкодов |
| resource_provenance_coverage, % | 100 × использованных музыкальных/звуковых ресурсов с проверенными источником, условиями и подтверждением / использованных ресурсов | 100% | Количество ресурсов без подтверждения и доля покрытия |
| requested_beat_alignment, % | 100 × помеченных для ритмической склейки стыков с min_abs(cut_t − beat_t) ≤ ε / всех таких стыков | ≥ 70% только для соответствующего стиля; стартовое ε = 80 мс | Гистограмма расстояния до акцента и линия ε |

Для speech_mix_pass используем отдельные речевой и музыкальный стемы после применённых gain/ducking. Окна по 400 мс размечены как речь; сравнивается RMS на одной временной сетке. Окно с требуемой, но потерянной речью считается ошибкой; нулевой музыкальный сигнал означает отсутствие маскирования, а не деление на ноль. Без наложенной музыки метрика not_applicable. Значение 6 dB — настраиваемая инженерная эвристика; пригодность подтверждается человеческой разборчивостью, которую она не заменяет.

Ритм оценивается только там, где он требуется сценарием. Карта ударов строится по выбранному музыкальному фрагменту с учётом обрезки, скорости и смещения. На контрольном наборе акценты сверяются вручную. Сохранение речи и обязательных сцен важнее попадания в удар; такие стыки исключаются из применимости заранее.

Отсутствие музыки допустимо, когда соответствует запросу. Если музыка требовалась, её отсутствие — невыполнение задания, а не not_applicable. Метрика происхождения проверяет наличие подтверждения и разрешённый политикой сценарий использования, а не автоматически выносит юридическое заключение.

## 5. Монтажный агент

| ID и единица | Как проверяем | Начальная цель | График |
|---|---|---|---|
| bad_boundary_rate, дефектных стыков / 100 | 100 × стыков с хотя бы одним подтверждённым дефектом / проверенных стыков | ≤ 2; критических дефектов 0 | Среднее по проектам с интервалом и столбцы причин |
| broken_speech_boundaries, % | 100 × границ с непредусмотренным обрывом слова/фразы / проверенных границ, затрагивающих речь | 0 обрывов слова; фразы — отдельная человеческая оценка | Число и таймкоды дефектов по версии |
| effect_parameter_validity, % | 100 × экземпляров эффектов, допустимых по версии пресета, параметрам, ресурсам и длительности / применённых экземпляров | 100% | Ошибки по пресету и версии |
| style_approval, % | 100 × случаев с человеческой оценкой соответствия стилю ≥ 4 / оценённых случаев | ≥ 80% | Распределение 1–5 и одобрение по стилю |
| title_readability_approval, % | 100 × проверенных титров без проблем шрифта, обрезки, времени чтения и контраста / проверенных титров | ≥ 95%; отсутствующих глифов и обрезки обязательного текста 0 | Доля и типы проблем с кадрами-примерами |
| preserved_edit_constraints, % | 100 × исполненных атомарных требований правки / применимых требований | 100% для жёстких ограничений | Матрица «тип команды × версия» |

bad_boundary_rate оценивает интервал вокруг склейки, например ± 0,5 с с расширением до полной длительности перехода. Дефектами считаются непредусмотренный пустой кадр/скачок, неправильное наложение, заметная ошибка скорости и обрыв речи; код и разметчик сохраняют тип и таймкод. Один стык с тремя дефектами один раз входит в числитель доли, но все три причины видны в деталях. Художественно намеренная резкая склейка не считается ошибкой.

Проблемы внутри длинного клипа учитываются отдельным списком и в технических проверках фильма; нулевая частота дефектов стыков не доказывает отсутствие других дефектов. При отсутствии стыков — not_applicable.

Субъективную перегруженность эффектами оценивает style_approval. Простое «чем меньше эффектов, тем лучше» не используется. Для титров код проверяет шрифты и safe area, а человек оценивает читаемость в реальном темпе просмотра.

## 6. Рецензент

Рецензент оценивается на отдельном наборе из чистых фильмов и копий с известными внесёнными дефектами. Начальный объём: минимум 40 вариантов с дефектами и 40 чистых контролей, с разными типами и тяжестью. Варианты одного исходного проекта образуют одну статистическую группу. Эталонные метки и информация о внесении дефекта рецензенту не передаются.

Предупреждение сопоставляется с эталонным дефектом один к одному: тот же тип, тот же клип/объект и временное пересечение IoU ≥ 0,3; для точечной ошибки допускается расстояние ≤ 0,5 с. Эти параметры версионируются вместе со scorer. Повторное сообщение о том же дефекте не даёт второй TP; дубли считаются отдельной метрикой. Спорные новые замечания разбирает независимый человек до фиксации эталона.

| ID | Формула | Начальная цель | График |
|---|---|---|---|
| reviewer_precision | TP / (TP + FP) | ≥ 0,90 | Диаграмма precision × recall по версиям |
| reviewer_recall | TP / (TP + FN) | ≥ 0,90 | Та же диаграмма + разбиение по типу ошибки |
| critical_defect_recall | TP_critical / (TP_critical + FN_critical) | 1,00 на контрольном наборе | Абсолютное число пропущенных критических ошибок |
| clean_false_alarm_rate | Чистых фильмов с хотя бы одним ложным предупреждением / всех чистых фильмов | ≤ 0,05 | Доля и типы ложных тревог |
| duplicate_warning_rate | Повторных сообщений о уже сопоставленном дефекте / всех сообщений | ≤ 0,05 | Доля по версии |

TP — найденный реальный дефект, FP — неподтверждённое предупреждение, FN — пропущенный дефект. При отсутствии предупреждений precision не определён; recall при наличии ошибок равен нулю. Точное определение позволяет не награждать рецензента, который называет ошибкой каждый кадр или не сообщает ничего.

## 7. Скорость, расходы и стабильность

| ID и единица | Подсчёт | Критерий и график |
|---|---|---|
| time_to_valid_preview, с | От принятия запроса до доступного проверенного превью, включая очереди и повторы | p50/p95 по одинаковому профилю; график p95 и распределение; ухудшение > 20% расследуется |
| agent_active_seconds, с | Сумма времени активных этапов конкретной роли, отдельно от ожидания очереди | По роли и версии; распределение, не сумма параллельных этапов как wall time |
| ai_cost_per_input_minute, USD/мин | Суммарная известная стоимость всех вызовов и повторов / суммарные минуты исходников принятых запусков | Сравнение на одном наборе; рост > 20% расследуется |
| ai_cost_per_success, USD/фильм | Все затраты набора, включая неуспешные попытки / число успешно выданных фильмов | Точки «качество × стоимость»; при 0 успехов — undefined, расходы остаются видны |
| correction_rounds | Число полных циклов творческой доработки до результата | p50/p95; максимум 2 по архитектуре |
| budget_exhaustion, % | 100 × запусков, упёршихся в ограничение / всех принятых запусков | Разбивка по времени/стоимости/шагам; целевой предел на контрольном наборе ≤ 5% |
| cost_measurement_coverage, % | 100 × вызовов с рассчитанной стоимостью / оплачиваемых вызовов | 100% для сравнения стоимости; иначе значение помечается неполным |

Тарифы, валюта и версия расчёта фиксируются. Суммы разных валют не складываются без заданного курса/даты. Для априорной оценки и фактического расхода используются разные поля. Значение USD — единица учёта, не предложение текущего тарифа провайдера.

p95 времени готовности считается среди успешных запусков с обязательным показом end_to_end_success и числа таймаутов рядом. Неуспех не становится «быстрым ответом»; отдельно показывается доля выполнения в deadline. На малом количестве успешных запусков p95 отмечается как нестабильный.

## 8. Человеческая разметка и калибровка LLM-оценки

Рубрика 1–5 применяется отдельно к связности, музыке и стилю:

- 1: явно противоречит запросу, существенные проблемы.
- 2: частично соответствует, требуется заметная переработка.
- 3: приемлемо, но есть конкретные заметные недостатки.
- 4: соответствует запросу, только небольшие недостатки.
- 5: полностью соответствует, заметных недостатков нет.

Два человека независимо оценивают результат, не видя имя модели и номер версии. Порядок A/B случайный. Для несовпадения решения «≥ 4 / < 4» или разницы оценок более одного балла добавляется третий разметчик; итог — медиана. Сохраняются исходные голоса, итог и короткое наблюдаемое обоснование с таймкодом. Различия вкуса не скрываются одним числом.

Попарное сравнение дополнительно фиксирует W (кандидат лучше), T (равно), L (хуже). Preference = (W + 0,5T) / (W + T + L). Ничьи показаны отдельной долей, 0,5 означает паритет. Это отдельный показатель предпочтения, не смешанный балл остальных метрик.

LLM-судья получает ту же рубрику и проверяемые материалы. На поднаборе с человеческим эталоном строим confusion matrix для approved / not_approved и измеряем balanced accuracy = (recall_approved + recall_not_approved) / 2. Начальная цель калибровки ≥ 0,85; ниже модельная серия остаётся диагностической. Калибровка повторяется при смене judge/prompt, результаты человека и модели подписаны отдельно. Подход сопоставления судьи с человеческими оценками описан в [документации Google](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/models/evaluate-judge-model).

## 9. Неопределённость и правила сравнения версий

Для мягких метрик строим 95% интервалы кластерным bootstrap: 2 000 раз выбираем с возвращением независимые исходные проекты, сохраняя внутри каждого все связанные случаи и повторы; для разницы версий используем одни и те же выбранные пары проектов. На малом наборе интервалы приблизительны. Фиксируем seed, scorer_version и способ вычисления процентилей.

Если все наблюдения одинаковы, обычный bootstrap может дать интервал нулевой ширины: его отмечаем как неинформативный и не используем для заявления о нулевом риске. Для решений о редких ошибках дополнительно собирается больший независимый набор и заранее выбирается соответствующий метод оценки границы частоты.

Сопоставляются одинаковые case_id/trial или заранее заданные пары. Новые/пропавшие случаи видны отдельным счётчиком; сравнение на пересечении нельзя выдавать за полный набор. Для изменённого состава suite строится отдельная серия либо обе версии пересчитываются на новом наборе. В графиках реальных пользователей меняется состав загрузок, поэтому они не являются причинным доказательством улучшения модели.

Допуск к выпуску:

1. Ноль критических нарушений и пропусков известных критических дефектов; все обязательные проверки имеют результат.
2. Выполнены технические цели и end_to_end_success. Проверка не должна улучшать долю, исключая упавшие случаи.
3. Для покрытия событий нижняя граница 95% интервала Δ(candidate − baseline) не ниже −3 процентных пунктов; для human approval — не ниже −5 п.п.
4. Для bad_boundary_rate верхняя граница интервала Δ не выше +1 п.п.; абсолютная цель также проверяется.
5. Для preference нижняя граница интервала не ниже 0,45. Если интервал слишком широк, статус «недостаточно данных», а не «без ухудшения».
6. Рост времени или стоимости > 20% требует разбора и явного изменения профиля, если он оправдан улучшением результата.

Допуски фиксируются до прогона и уточняются на реальных данных. Каждая обязательная метрика проверяется отдельно, средний общий балл не компенсирует провал. Если несколько вариантов перебирались на holdout, нужен новый независимый подтверждающий набор; иначе выбор лучшего по шуму исказит оценку.

0 нарушений в конечном числе проверок означает только отсутствие обнаруженных нарушений в этой выборке. На графике всегда остаются N и число независимых проектов.

## 10. Сбор и хранение результатов

Поток: manifest контрольного набора → фиксированный запуск → план/рендер → детерминированные scorers → независимые оценки → агрегаты и интервалы → сравнение с baseline → решение CI.

При реализации добавляем две таблицы PostgreSQL:

| Таблица | Поля и назначение |
|---|---|
| eval_runs | run_id, suite/version/hash, split, configuration_hash, версии модели/промптов/инструментов/scorers, baseline_run_id, hardware_profile, seed, время, статус, manifest_object_id |
| eval_results | run_id, case_id, corpus_id, trial, role, metric_id/version, evaluator_id, numerator, denominator, value, unit, status/reason, source (code/human/llm), evidence_object_id, target_version_id, время |

Одна строка eval_results — одна метрика одного случая/повтора от конкретного оценщика. Уникальность по run/case/trial/metric_version/evaluator не допускает двойного учёта при повторах записи. Сырые человеческие голоса и итоговый consensus имеют разные evaluator_id; агрегатор использует только выбранный тип результата. Неприменимость, отсутствие оценки и ошибка представлены явными статусами, не нулевыми значениями.

Исходники, небольшие доказательные клипы, отчёты и разметка хранятся в закрытом S3; таблицы содержат численные результаты и ссылки. Идентификаторы внутренних тестовых проектов не дают доступ к пользовательским проектам. Журнал agent_steps и ai_calls — входы для измерений; сам факт успешного tool call не является подтверждением художественного качества.

SQL-схема сейчас остаётся базовой: эти таблицы потребуют миграции при реализации evaluator. Манифесты и формулы версионируются; повторная оценка создаёт новый run и сохраняет старый.

Для Grafana создаём ограниченные read-only SQL-представления агрегатов. В Prometheus остаются эксплуатационные счётчики/гистограммы с ограниченными labels: role, stage, outcome, настроенный model_alias. case_id/run_id/произвольные prompt_version не становятся labels. p95 между worker вычисляется из объединённых histogram buckets, а не средним от отдельных p95. [Prometheus: агрегация гистограмм](https://prometheus.io/docs/practices/histograms/).

## 11. Дашборд оценки

Оператор выбирает baseline и candidate, suite/version/split, роль и тип материала. Источник оценки (код/человек/LLM) всегда виден. Фильтр меняет также N и статус достаточности данных. Страница оценки является административной; обычный пользователь видит фильм, статус и объяснение правки.

| Панель | Оси и представление | Обязательная детализация |
|---|---|---|
| Исполнение | X: версия; Y: end_to_end_success и first_plan_valid в раздельных графиках, % | Успехи/все, проекты/случаи/повторы, missing и CI |
| Жёсткие правила | X: версия; Y: число нарушающих финальных результатов | Тип нарушения, case, сообщение, версия и таймкод |
| Режиссёр | X: версия; Y: salient_event_coverage, % | Пропущенные события и веса; story approval/повторы отдельными панелями |
| Музыка | X: версия; Y: music_fit_approval, % | Голоса, распределение 1–5; разборчивость и происхождение отдельными панелями |
| Монтаж | X: версия; Y: bad_boundary_rate на 100 стыков | Дефектные/проверенные стыки, тип, превью вокруг границы |
| Рецензент | X: precision, %; Y: recall, %; одна точка на версию | TP/FP/FN, критические пропуски, ложные тревоги на чистых фильмах |
| Время | X: версия или дата; Y: time_to_valid_preview p95, с | p50, число успешных и таймаутов, очередь отдельно от активного времени |
| Расход | X: версия; Y: ai_cost_per_input_minute, USD/мин | Общая стоимость, повторные вызовы, полнота расчёта; отдельный график стоимости успешного фильма |
| Сравнение | X: Δcandidate−baseline; Y: метрики в отдельных шкалах | 95% интервал, допуск, число сопоставленных проектов и решение |
| Калибровка | Матрица человеческой и модельной оценки | Число объектов, balanced accuracy, класс и версия судьи |

Показываем абсолютные значения, относительное изменение и разницу долей в процентных пунктах раздельно. У количественных осей есть единицы; частоты для столбцов начинаются с нуля. При увеличенной шкале точечного графика её границы явно видны. Нельзя объединять стоимость, проценты и секунды на общей шкале.

Интервалы рисуются полосой или усами; точка без интервала указывает на описанный ограниченный режим оценки, а не на нулевую неопределённость. Неизвестное отображается пропуском с причиной. Клик по точке открывает соответствующие случаи, доказательные клипы и расхождения без повторного запуска агента. Линия критерия подписана как проектная цель.

В диалоге показан компактный интерактивный пример основных панелей на синтетическом наборе. Он демонстрирует формат графиков и выбор версии; не подключён к мониторингу и не является отчётом качества VMerger. Полный рабочий дашборд реализуется после evaluator.

В демонстрации один случай на проект и три повтора: 90 запусков на каждую из пяти версий. Значения вычислены из синтетических наблюдений с фиксированным seed, а интервалы — по 2 000 выборкам проектов. Это уменьшенный пример, а не полный контрольный набор с несколькими видами правок и чистыми контрольными фильмами для рецензента.

## 12. Проверка самих метрик

Scorers имеют собственные тесты с ручным ожидаемым результатом:

- Сохранены 8 из 10 событий одинакового веса → coverage = 80%; при нуле применимых событий → not_applicable.
- Из 40 проверенных стыков два дефектных → bad_boundary_rate = 5; три дефекта одного стыка не увеличивают число дефектных стыков до трёх.
- TP = 9, FP = 3, FN = 1 → precision = 75%, recall = 90%; дубли предупреждений не создают TP.
- Побед 6, ничьих 2, поражений 2 → preference = 70%; число оценённых пар 10.
- Из 10 принятых запусков 8 успешны, один упал и один истёк → success = 80%, а не 100% по завершённым фильмам.
- Стоимость всех попыток 12 USD, успешно 8 фильмов → ai_cost_per_success = 1,50 USD; отсутствующая стоимость вызова снижает coverage и помечает сумму неполной.
- Обновление временной карты при скорости/переходе правильно переносит границы речи и музыкальных акцентов.
- Подсчёт micro и macro на наборе с разной длиной фильмов даёт разные, заранее рассчитанные значения.
- Повторные записи, несколько разметчиков, missing, нулевой знаменатель и пустой baseline не улучшают агрегат.
- Bootstrap сохраняет связанные случаи/повторы проекта и пары версий; смена порядка строк не меняет результат при фиксированных seed и сортировке.
- Дашборд показывает тот же numerator/denominator, что evaluator; переключение фильтра пересчитывает N; шкалы и подписи не скрывают регрессию.

До внедрения автоматической оценки один и тот же небольшой набор независимо считают вручную и scorer. Ошибки evaluator блокируют решение о выпуске наравне с ошибками приложения.
